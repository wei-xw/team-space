# 团队空间（Team Space）产品需求文档

> 版本：v0.1-draft | 日期：2026-06-05
> 
> 定位：面向 AI 编程工具（Cursor / Codex / Claude Code）使用者的团队协作平台，通过共建知识库、技能、工具和对话沉淀，实现团队级 AI 提效。

---

## 一、背景与问题

### 1.1 现状

团队成员已在使用 Cursor、Codex、Claude Code 等 AI 编程工具辅助日常工作，但存在以下问题：

- **个人孤岛**：每个人独立探索 prompt 技巧、工作流，经验无法共享
- **知识断层**：项目背景、业务上下文散落在各处，AI 工具无法获取完整上下文
- **重复踩坑**：同类型问题被不同人反复向 AI 描述，没有形成可复用的 skill
- **优秀实践流失**：精彩的 AI 对话（如一次高质量的技术方案生成）仅存在于个人会话中，未被识别和推广

### 1.2 核心洞察

> 参考 YC 内部 Agent 系统的经验：真正的 AI-Native 组织和「把 AI 当 Copilot 用」的组织有本质差异。Copilot 模式下流程、决策、知识仍然在人的头脑里；AI-Native 模式把 AI 作为组织运转的基础层，系统性记录所有 artifacts（会议录音、Agent 对话、决策文档），让 Agent 可以学习、检索、利用。

我们的产品理念：

- **Trust by Default**（默认信任）：团队内对话默认对全员可见，AI 才能获得足够广的上下文
- **Egalitarian**（平等主义）：AI 能力向每个人开放，不只是管理层或技术专家
- **Agent Wrapping Tools**：让 AI 包裹确定性工具，而非在确定性工具里嵌一小块 AI
- **最小化预写代码**：最佳 AI 软件往往是最小的，让模型做最多的工作

## 二、产品定位与目标用户

### 2.1 一句话定位

**Team Space** —— 团队的 AI 协作操作系统：共建知识、共享技能、沉淀对话、自动优化。

### 2.2 目标用户

| 角色 | 核心诉求 |
|------|---------|
| 研发工程师 | 快速了解项目背景、复用优秀的 prompt 和 skill、减少重复劳动 |
| 产品经理 | 维护需求文档，让 AI 理解业务上下文后生成更精准的方案 |
| 测试工程师 | 基于需求文档和代码变更自动生成测试用例 |
| 技术负责人 | 发现团队中优秀的 AI 实践并推广、了解团队 AI 使用状况 |
| 新入职成员 | 通过系统快速获得项目上下文，跳过半年的「摸索期」 |

### 2.3 核心价值主张

1. **知识即上下文**：AI 不再「失忆」，每次对话都站在团队知识库的肩膀上
2. **技能可共创**：一个人摸索出的 skill，全队可一键使用
3. **对话即资产**：优秀的 AI 对话被识别、提炼、反哺整个团队
4. **持续自进化**：AI 每晚自动分析对话，改进自身技能

## 四、核心模块详细设计

### 模块一：知识库（Knowledge Base）

#### 4.1.1 定义

知识库是团队共享的上下文中心，存放 AI 需要理解的背景信息，让每次 AI 对话都能引用团队积累的知识。

#### 4.1.2 内容类型

| 类型 | 说明 | 示例 |
|------|------|------|
| 需求文档（PRD） | 产品需求说明 | OA 审批流程 PRD、CRM 客户管理 PRD |
| 技术方案 | 架构设计、API 文档 | 微服务拆分方案、接口文档 |
| 业务规则 | 业务逻辑说明 | 定价策略、权限模型 |
| 项目规范 | 编码规范、发布流程 | Git Flow 规范、Code Review Checklist |
| FAQ | 常见问题及解答 | 环境配置指南、历史踩坑记录 |

#### 4.1.3 分类体系（双维度标签）

知识库采用**双维度标签分类**，用户可自定义标签：

**维度一：业务域（Business Domain）**
- 用户自定义，如：`OA`、`销售CRM`、`招聘系统`、`财务平台`、`内部工具`

**维度二：工作环节（Work Phase）**
- 预置 + 可自定义，如：`需求分析`、`UI设计`、`开发`、`测试`、`发布`、`运维`

每个文档可同时标记多个业务域标签和工作环节标签。

```
示例：
  文档：《CRM 客户跟进流程 PRD v3》
  标签：[销售CRM] [需求分析]
  
  文档：《OA 审批引擎技术方案》
  标签：[OA] [开发]
  
  文档：《统一权限模型设计》
  标签：[OA, 销售CRM, 招聘系统] [开发]
```

#### 4.1.4 知识库与 AI 工具的集成方式

- **Markdown 优先**：所有文档以 Markdown 格式存储，天然兼容 AI 工具的上下文注入
- **自动注入**：当 AI 工具处理与某个业务域相关的任务时，自动将相关文档作为上下文注入
- **手动引用**：用户可在对话中 `@文档名` 引用特定文档
- **版本管理**：文档基于 Git 管理，支持 diff 和 history

#### 4.1.5 知识库管理

| 功能 | 说明 |
|------|------|
| 创建/编辑 | 支持在线编辑、本地编辑器同步、API 导入 |
| 审核机制 | 重要文档修改需 Review（可配置） |
| 搜索 | 全文搜索 + 标签筛选 + 语义搜索 |
| 过期提醒 | 文档长期未更新时提醒维护 |
| 关联追踪 | 记录哪些对话引用了该文档 |

### 模块二：技能系统（Skills Registry）

#### 4.2.1 定义

技能是「教 AI 怎么做」的标准化指令包。一个 skill 包含 AI 执行特定任务所需的 prompt 模板、工具调用流程、输出规范等。

> 参考 YC 的做法：技能系统就像一个内部注册表，每个技能可以被任何人调用，AI 每晚还会自动阅读对话来改进这些技能。

#### 4.2.2 Skill 结构规范

```yaml
# skill.yaml 示例
name: generate-api-doc
version: 1.2.0
author: 张三
description: 根据代码自动生成 API 文档
tags:
  business: [OA, 销售CRM]     # 适用业务域
  phase: [开发]                # 适用工作环节
trigger_keywords:               # 触发关键词
  - "生成API文档"
  - "接口文档"
  - "API doc"

# 技能指令
instructions: |
  你是一个 API 文档专家。请根据提供的代码文件，生成标准的 API 文档。
  
  输出格式要求：
  1. 接口概述（一句话说明用途）
  2. 请求方式 + 路径
  3. 请求参数（表格形式）
  4. 响应参数（表格形式）
  5. 错误码说明
  6. 调用示例
  
  参考规范文档：{{knowledge:api-doc-standard}}  # 引用知识库

# 依赖的工具（可选）
tools:
  - name: read-file
    description: 读取代码文件
  - name: search-code
    description: 搜索代码库

# 输出示例（few-shot）
examples:
  - input: "请根据 user_controller.go 生成API文档"
    output: |
      ## 用户管理接口
      ...

# 质量指标
metrics:
  success_rate: 0.92          # 历史成功率
  avg_satisfaction: 4.3       # 平均满意度（1-5）
  usage_count: 156            # 总使用次数
  last_improved: 2026-06-01   # 上次优化日期
```

#### 4.2.3 Skill 生命周期

```
创建 → 审核 → 发布 → 使用 → 评价 → 分析优化 → 迭代更新 → (废弃)
```

| 阶段 | 说明 |
|------|------|
| 创建 | 任何成员可提交新 skill 或 fork 已有 skill |
| 审核 | 团队 review（初期可简化为自动发布 + 事后审核） |
| 发布 | 进入团队技能注册表，全员可用 |
| 使用 | 成员在 AI 工具中调用，系统记录使用数据 |
| 评价 | 使用后自动收集满意度反馈 |
| 分析优化 | AI 分析使用数据，建议 skill 改进（见模块六） |
| 迭代更新 | 作者确认后发布新版本 |
| 废弃 | 长期无人使用或已被更好方案替代时归档 |

#### 4.2.4 Skill 分类

同样采用**业务域 + 工作环节**双维度标签，与知识库统一分类体系。

#### 4.2.5 Skill 发现与推荐

- **按场景推荐**：根据当前文件类型、Git 分支名、commit message 推荐相关 skill
- **热门排行**：按使用次数、满意度排序
- **智能搜索**：支持自然语言描述需求，匹配最合适的 skill

### 模块三：工具注册表（MCP/Tools Registry）

#### 4.3.1 定义

工具注册表管理团队可用的 MCP Server 和自定义工具，让 AI 具备「做事」的能力。

> 参考 YC 的经验：他们从 3 个工具开始（SQL 查询、模型文件读取、执行），最终演化为 350+ 工具的内部注册表。关键是渐进式开放权限。

#### 4.3.2 工具类型

| 类型 | 说明 | 示例 |
|------|------|------|
| MCP Server | 标准 MCP 协议的工具服务 | 数据库查询、Jira 集成、GitLab 集成 |
| 自定义脚本 | 团队编写的工具脚本 | 代码生成器、数据迁移脚本 |
| API 封装 | 内部 API 的安全封装 | 用户查询、配置管理 |

#### 4.3.3 工具注册表结构

```yaml
# tool.yaml 示例
name: db-query-readonly
version: 1.0.0
author: 李四
description: 只读查询生产数据库（OA 业务库）
tags:
  business: [OA]
  phase: [开发, 测试, 运维]

# 权限分级
permission_level: safe         # safe / caution / dangerous
requires_approval: false       # safe 级别无需审批

# 运行配置
runtime:
  type: mcp                    # mcp / script / api
  endpoint: "{{local_config:db_readonly_url}}"  # 引用本地配置
  timeout: 30s

# 安全约束
constraints:
  read_only: true
  max_rows: 1000
  allowed_tables: ["users", "orders", "departments"]
  blocked_operations: ["DROP", "DELETE", "UPDATE", "INSERT"]
```

#### 4.3.4 权限分级模型

借鉴 YC 的渐进式开放策略：

| 级别 | 说明 | 审批要求 | 示例 |
|------|------|---------|------|
| **Safe** | 只读、无副作用 | 无需审批 | 数据库只读查询、读文件 |
| **Caution** | 有写入但可回滚 | 使用时通知团队 | 创建文档、发通知 |
| **Dangerous** | 不可逆操作 | 需人工确认 | 删除数据、发布上线 |

#### 4.3.5 工具与本地配置的关系

工具的敏感配置（数据库地址、API Key 等）不存储在团队空间，而是引用**本地配置**（见模块四）。

### 模块四：本地配置管理（Local Config）

#### 4.4.1 设计原则

> 敏感信息（密钥、个人 Token、本地路径等）绝不上传到团队空间。团队空间只定义配置的 Schema（字段名、类型、描述），成员在本地自行填写。

#### 4.4.2 配置机制

**团队空间定义配置 Schema：**

```yaml
# local-config-schema.yaml（存储在团队空间）
configs:
  - key: openai_api_key
    type: secret
    description: OpenAI API Key，用于调用 GPT 系列模型
    required: true
    hint: "从 https://platform.openai.com/api-keys 获取"
    
  - key: db_readonly_url
    type: string
    description: 只读数据库连接字符串
    required: false
    hint: "格式: postgresql://user:pass@host:5432/dbname"
    
  - key: gitlab_token
    type: secret
    description: GitLab Personal Access Token（需 read_repository 权限）
    required: true
    
  - key: local_workspace
    type: path
    description: 本地工作目录路径
    required: false
    default: "~/workspace"
```

**成员本地配置文件：**

```yaml
# ~/.team-space/local-config.yaml（不上传，不进入 Git）
openai_api_key: "sk-xxxxx"
db_readonly_url: "postgresql://zhangsan:pass@10.0.0.1:5432/oa_db"
gitlab_token: "glpat-xxxxx"
local_workspace: "/Users/zhangsan/workspace"
```

#### 4.4.3 运行时配置读取流程

```
AI 工具发起请求
    │
    ▼
Skill/Tool 引用 {{local_config:key_name}}
    │
    ▼
Team Space Runtime 读取本地 ~/.team-space/local-config.yaml
    │
    ├── 配置存在 → 注入实际值 → 继续执行
    │
    └── 配置缺失 → 提示用户填写
         "需要配置 db_readonly_url（只读数据库连接字符串）"
         "请在 ~/.team-space/local-config.yaml 中添加"
```

#### 4.4.4 安全性保障

| 措施 | 说明 |
|------|------|
| 本地文件 `.gitignore` | 自动配置 gitignore，防止误提交 |
| 加密存储 | 本地 `secret` 类型配置使用系统 Keychain 加密（macOS Keychain） |
| 脱敏展示 | 日志和 UI 中 secret 类型配置仅显示 `****` |
| 权限最小化 | 运行时只注入当前操作所需的配置项 |

### 模块五：对话采集（Conversation Capture）

#### 4.5.1 目标

自动采集成员在 Cursor、Codex、Claude Code 等 IDE 中的 AI 对话数据，作为分析和优化的数据源。

#### 4.5.2 采集范围

| 数据项 | 说明 | 采集方式 |
|--------|------|---------|
| 对话消息 | 用户 prompt + AI 回复（完整内容） | 监听本地会话文件 |
| 上下文信息 | 当前文件名、项目名、Git 分支 | 本地采集脚本获取 |
| 使用的 Skill/Tool | 对话中调用了哪些技能和工具 | 对话内容解析 |
| 时间戳 | 对话开始/结束时间 | 本地记录 |
| 用户反馈 | 用户对 AI 回复的评价（thumbs up/down） | 如 IDE 支持则采集 |
| 执行结果 | 代码是否被采纳、测试是否通过 | 如可获取则采集 |

#### 4.5.3 监听脚本设计（初期 Mac 脚本方案）

```
架构：
┌────────────────────────────────────────────┐
│  Mac 本地                                  │
│                                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │ Cursor   │  │  Codex   │  │Claude Code│ │
│  │ 会话文件  │  │ 会话文件  │  │ 会话文件  │ │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘ │
│       │              │              │       │
│       └──────────────┼──────────────┘       │
│                      ▼                      │
│           ┌──────────────────┐              │
│           │  File Watcher    │ (fswatch)    │
│           │  监听会话文件变化  │              │
│           └────────┬─────────┘              │
│                    ▼                        │
│           ┌──────────────────┐              │
│           │  数据提取 & 清洗  │              │
│           │  - 解析对话格式   │              │
│           │  - 脱敏处理       │              │
│           │  - 附加上下文     │              │
│           └────────┬─────────┘              │
│                    ▼                        │
│           ┌──────────────────┐              │
│           │  本地暂存队列     │              │
│           │  (SQLite)        │              │
│           └────────┬─────────┘              │
└────────────────────┼────────────────────────┘
                     │ 定时上报（每 5 分钟）
                     ▼
           ┌──────────────────┐
           │  Team Space API  │
           │  POST /conversations
           └──────────────────┘
```

**各 IDE 会话文件路径（Mac）：**

| IDE | 会话存储位置 | 格式 |
|-----|-------------|------|
| Cursor | `~/Library/Application Support/Cursor/User/workspaceStorage/*/chat.json` | JSON |
| Codex | `~/.codex/sessions/` | JSON/JSONL |
| Claude Code | `~/.claude/projects/*/conversations/` | JSONL |

> 注：以上路径可能随 IDE 版本更新变化，需要维护一个路径映射配置，并在脚本中做好兼容。

#### 4.5.4 数据脱敏策略

| 脱敏项 | 处理方式 |
|--------|---------|
| API Key / Token | 正则匹配替换为 `[REDACTED]` |
| 密码 | 正则匹配替换为 `[REDACTED]` |
| 内部 IP 地址 | 保留网段，隐藏主机位（`10.0.0.*`） |
| 个人手机号/邮箱 | 正则匹配替换为 `[REDACTED]` |

#### 4.5.5 隐私与合规

- **用户知情同意**：首次安装时明确告知采集范围，需用户确认
- **个人控制权**：
  - 可随时暂停/恢复采集
  - 可选择「仅上报脱敏后的对话摘要」而非完整内容
  - 可标记某次对话为「私有」，不上报
- **数据保留策略**：原始对话保留 90 天，分析后的统计数据和提炼的 skill 永久保留
- **访问控制**：完整对话仅对话发起者和管理员可见，分析报告对全员可见

#### 4.5.6 安装与运行

```bash
# 一键安装
curl -fsSL https://team-space.internal/install.sh | bash

# 安装后：
# 1. 生成 ~/.team-space/ 目录结构
# 2. 交互式引导填写 local-config.yaml
# 3. 安装 launchd 服务（Mac 开机自启）
# 4. 启动 file watcher

# 管理命令
team-space status       # 查看运行状态
team-space pause        # 暂停采集
team-space resume       # 恢复采集
team-space stats        # 查看本地统计
```

### 模块六：对话分析与优秀对话发现（Conversation Analytics）

#### 4.6.1 设计目标

从海量对话中识别出「优秀对话」，即对团队有参考价值的高质量 AI 交互，并提炼为可复用的知识。

> 参考 YC：他们的系统每晚自动阅读当天所有 Agent 对话，改进自身技能。我们的分析引擎是实现这一闭环的核心。

#### 4.6.2 分析策略：多维度评分模型

采用**规则筛选 + LLM 评估**的两阶段策略。

**第一阶段：规则预筛（快速过滤，降低成本）**

以下对话直接进入候选池：

| 规则 | 条件 | 权重 |
|------|------|------|
| 用户正向反馈 | 用户点了 thumbs up / 明确表示满意 | 高 |
| 多轮有效交互 | 对话超过 3 轮且未出现重试/否定 | 中 |
| 产出被采纳 | 生成的代码被用户接受（未大幅修改） | 高 |
| 使用了团队 Skill | 对话中成功使用了已注册的团队 skill | 中 |
| 复杂度信号 | 涉及多文件、跨模块、架构级讨论 | 中 |
| 知识引用 | 对话中引用了知识库文档并产出有价值结果 | 中 |

以下对话被排除：

| 规则 | 原因 |
|------|------|
| 纯闲聊/测试 | "你好"、"test" 等无实质内容 |
| 含敏感信息 | 脱敏后信息损失过大，无法理解 |
| 对话中断 | 少于 2 轮即结束 |
| 用户明确否定 | "这不对"、"重新来" 等负反馈多 |

**第二阶段：LLM 深度评估（对候选对话精细打分）**

对通过预筛的对话，使用 LLM 从以下维度评分（每维 1-5 分）：

| 评估维度 | 评分标准 | 权重 |
|----------|---------|------|
| **问题质量** | 提问是否清晰、结构化、有上下文 | 20% |
| **回答质量** | AI 回复是否准确、完整、可执行 | 25% |
| **过程质量** | 对话过程是否高效，有无不必要的反复 | 15% |
| **可复用性** | 对话中的方法/思路是否可推广到类似场景 | 25% |
| **教育价值** | 其他成员能否从中学到新的技巧或知识 | 15% |

**综合得分计算：**

```
final_score = Σ(维度得分 × 权重) / 5

优秀阈值：final_score ≥ 0.75（满分 1.0）
精选阈值：final_score ≥ 0.90
```

#### 4.6.3 分析执行流程

```
每日定时任务（凌晨 2:00）
    │
    ▼
获取前一日所有对话
    │
    ▼
第一阶段：规则预筛
    │ 过滤掉 ~80% 低价值对话
    ▼
第二阶段：LLM 深度评估
    │ 对 ~20% 候选对话打分
    ▼
生成分析报告
    │
    ├── 优秀对话列表（按得分排序）
    │
    ├── 模式识别结果：
    │   - 高频问题类型
    │   - 成功模式（哪些 prompt 结构效果好）
    │   - 失败模式（哪些做法容易走弯路）
    │
    ├── Skill 改进建议：
    │   - 哪些 skill 使用频率高但满意度低 → 需要优化
    │   - 哪些高频场景还没有对应 skill → 需要新建
    │   - 哪些 skill 的 prompt 可以被优秀对话中的表述替代
    │
    └── 知识库更新建议：
        - 对话中暴露的文档缺失
        - 文档过时或不准确的地方
```

### 模块七：AI 自动优化（AI Self-Improvement）

> 这是整个系统的核心价值闭环：对话数据 → 分析洞察 → 自动优化 → 更好的对话。
> 参考 YC：他们的系统每晚自动阅读当天所有对话，改进自身技能。在某些具体能力上，已经超过了任何一位合伙人单独的水平。

#### 4.7.1 优化的范围与边界

**核心原则：优化 Skill 和 Knowledge，不直接修改业务代码。**

| 优化对象 | 可自动执行 | 需人工确认 | 说明 |
|----------|-----------|-----------|------|
| Skill prompt 措辞微调 | ✅ | | 如替换模糊表述为更精确的措辞 |
| Skill 新增 few-shot 示例 | ✅ | | 从优秀对话中提取新的示例 |
| Skill 参数/格式调整 | | ✅ | 如改变输出格式要求 |
| Skill 逻辑流程变更 | | ✅ | 如增加/删除步骤 |
| 新建 Skill | | ✅ | AI 建议 + 人工审核 |
| 知识库文档更新 | | ✅ | AI 建议修正，人工确认 |
| 知识库新增文档 | | ✅ | AI 建议补充，人工确认 |
| 工具配置变更 | | ✅ | 安全相关，必须人工审批 |
| 工具代码修改 | | ✅ | 安全相关，必须人工审批 |

#### 4.7.2 优化策略详解

**策略一：Prompt 蒸馏（Prompt Distillation）**

从优秀对话中提取高效的 prompt 模式，反哺到 skill 中。

```
原始 skill prompt：
  "请根据代码生成API文档"

从优秀对话中蒸馏后的 prompt：
  "请根据代码生成 API 文档。
   要求：
   1. 先列出所有公开接口，标注 HTTP 方法和路径
   2. 参数用表格展示，标注类型、是否必填、说明
   3. 每个接口附带一个 curl 调用示例
   4. 如果接口有权限控制，单独说明权限要求"
```

蒸馏流程：
1. 收集使用某 skill 的所有对话
2. 筛选出高满意度对话
3. 提取这些对话中用户 prompt 的共同特征
4. 与当前 skill prompt 对比，生成改进建议
5. 自动应用低风险的措辞调整，高风险的变更等待人工确认

**策略二：失败模式修复（Failure Pattern Fix）**

识别对话中的常见失败模式，针对性修复。

```
失败模式示例：
  - AI 反复生成不符合团队编码规范的代码
    → 根因：skill 未注入编码规范
    → 修复：在 skill 中增加 {{knowledge:coding-standards}} 引用

  - AI 在生成 SQL 时总是忘记加 LIMIT
    → 根因：skill 未约束查询范围
    → 修复：在 skill 指令中增加 "所有查询必须包含 LIMIT 1000"
```

**策略三：知识库自动补全（Knowledge Gap Fill）**

从对话中发现知识库的缺失或过时内容。

```
信号检测：
  - 用户在对话中手动补充了大量业务背景
    → 说明知识库缺少这部分内容
    → AI 提取并建议新增文档

  - AI 给出的回答与用户纠正后的版本差异大
    → 说明知识库中相关内容过时或不准确
    → AI 生成修正建议
```

**策略四：新 Skill 孵化（Skill Incubation）**

当某类对话模式反复出现但尚无对应 skill 时，自动建议新建。

```
检测条件：
  - 过去 7 天内 ≥ 5 次对话涉及相似主题
  - 且这些对话没有使用任何现有 skill
  - 且其中 ≥ 2 次获得了高满意度评分

输出：
  - 自动生成 skill 草案（包含 prompt 模板、示例、适用场景）
  - 通知团队 review 并决定是否发布
```

#### 4.7.3 安全防护机制

> AI 自动优化必须可控、可审计、可回滚。

**防护层级：**

```
第一层：变更分级
    │
    ├── 低风险变更（自动执行）
    │   - prompt 措辞微调（不改变语义）
    │   - 新增 few-shot 示例
    │   - 新增触发关键词
    │
    ├── 中风险变更（需 1 人审批）
    │   - prompt 结构/流程调整
    │   - 新增/修改输出格式要求
    │   - 知识库内容更新
    │
    └── 高风险变更（需 2 人审批 + 测试）
        - 工具权限变更
        - 删除/废弃 skill
        - 修改安全约束

第二层：灰度发布
    │
    ├── A/B 测试：新版本先对 20% 成员生效
    │   - 对比新旧版本的成功率和满意度
    │   - 运行 3 天后根据数据决定是否全量
    │
    └── 自动回滚条件：
        - 新版本成功率比旧版本下降 > 15%
        - 新版本满意度评分下降 > 0.5 分
        - 出现安全相关异常

第三层：完整审计
    │
    ├── 所有变更记录：
    │   - 变更内容（diff）
    │   - 变更原因（基于哪些对话数据）
    │   - 变更时间、审批人
    │   - 变更后的效果数据
    │
    └── 一键回滚：
        - 任何时候可回滚到历史任意版本
        - 回滚自动通知团队
```

#### 4.7.4 优化效果度量

| 指标 | 计算方式 | 目标 |
|------|---------|------|
| Skill 成功率 | 使用 skill 的对话中，用户未否定/重试的比例 | 逐月提升 |
| 首次回复满意率 | AI 第一次回复就获得正向反馈的比例 | 逐月提升 |
| 对话轮次效率 | 完成同类任务的平均对话轮次 | 逐月下降 |
| 新 Skill 孵化率 | 每月从对话中新建的 skill 数量 | 保持增长 |
| 知识库覆盖率 | 团队成员提问后 AI 能引用相关文档的比例 | 逐月提升 |

## 八、可行性分析

### 8.1 技术可行性

| 模块 | 可行性 | 风险 | 应对策略 |
|------|--------|------|---------|
| 知识库 | ✅ 高 | 无重大技术风险 | 基于 Git 的成熟方案 |
| 技能系统 | ✅ 高 | Skill 格式需统一 | 参考 Codex/Cursor 的 skill 规范 |
| 工具注册表 | ⚠️ 中高 | 权限控制复杂 | 初期仅支持 safe 级别工具 |
| 本地配置 | ✅ 高 | macOS Keychain API 兼容性 | 先支持明文 YAML，后续加密 |
| 对话采集 | ⚠️ 中 | IDE 会话文件格式可能变化 | 做好兼容层 + 降级策略 |
| 对话分析 | ⚠️ 中 | LLM 评估成本、准确度 | 先用规则预筛降低 LLM 调用量 |
| AI 优化 | ⚠️ 中 | 自动修改可能引入问题 | 严格的变更分级和灰度发布 |

### 8.2 成本估算

| 项目 | 月估算成本 | 说明 |
|------|-----------|------|
| 服务器 | ¥500-2000 | 内网部署，一台 4C8G 即可起步 |

| 存储 | ¥100-500 | Git 仓库 + 数据库 |
| **合计** | **¥2600-10500/月** | 10-20 人团队规模 |

### 8.3 关键风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|

| 知识库维护懈怠 | 内容过时 | 中 | 过期提醒 + AI 自动检测过时内容 |

## 九、与现有工具的集成方案

### 9.1 Cursor 集成

- 通过 `.cursorrules` 文件注入团队 skill 和 knowledge
- 对话采集通过监听 Cursor 本地会话文件实现
- 未来可开发 Cursor 插件直接在 IDE 内浏览团队空间

### 9.2 Codex 集成

- 通过 `AGENTS.md` 和 `SKILL.md` 机制注入团队知识
- Codex 原生支持 skill 系统，可直接引用团队 skill
- 对话采集通过监听 `~/.codex/sessions/` 实现

### 9.3 Claude Code 集成

- 通过 `CLAUDE.md` 注入团队上下文
- 对话采集通过监听 Claude Code 的会话文件实现
- 利用 MCP 协议对接团队工具注册表

### 9.4 统一适配层

```
Team Space Runtime（本地 daemon）
    │
    ├── 读取团队空间配置（skill、knowledge、tools）
    │
    ├── 生成 IDE 特定配置文件：
    │   ├── .cursorrules（Cursor）
    │   ├── AGENTS.md / SKILL.md（Codex）
    │   └── CLAUDE.md（Claude Code）
    │
    ├── 监听各 IDE 会话文件
    │
    └── 管理本地配置注入
```
